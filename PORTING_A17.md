# Step 3: what was re-derived for Android 17, and what happened to each Android 16 fix

Done 2026-11-11 against stock A171WVH.21-16-16 and LineageOS 24.0 sources. Labels: **static**
= checked on files or sources; **build** = checked in the built image (filled in by the
validation run, see COMPATIBILITY.md). Nothing here is boot- or hardware-tested.

## Re-derived from the Android 17 firmware

| Item | Result | How |
|---|---|---|
| `proprietary-files.txt` | **34 entries** (32 files + 2 recreated symlinks), every one pinned to its A17 SHA-256. Against A16: `qti-telephony-hidl-wrapper` (jar + permission file) and `libimscamera_jni.so` (+ symlink) are gone because the A17 IMS app no longer uses them; `libSurfaceUtil_jni.so` (+ symlink) is new (a JNI library of the A17 IMS app); every other file is the same path with new content where Motorola rebuilt it (23 changed, 10 identical) | `resolve_components.py` on the A17 inventory, unchanged `components.json`; `extract-firmware.sh` stage `blobs` copied and checked them. `target-system-libs.txt` is regenerated from the LineageOS build output and the closure resolved again (BUILDING.md) |
| `properties.mk` | all values unchanged on A17; `persist.sys.dolby.upmapping.filter.notify` dropped (A17 stock no longer sets it) | `prop_users.py` on A17 vs A16 (FIRMWARE_A17.md section 4) |
| SELinux public types and mapping | `sepolicy/public` unchanged: the A17 vendor policy is version 202504 with the same rules on `vendor_qtelephony`, `moto_camera_app` and the four attributes. **Added** to `sepolicy/private/seapp_contexts`: stock's `name=com.qti.phone domain=vendor_qtelephony` line, because the A17 IMS app runs in the process `com.qti.phone`. **Added** `sepolicy/private/compat/202504/202504.cil`: LineageOS 24's platform policy version is 202604, so the build maps our public types only in `system_ext/etc/selinux/mapping/202604.cil`, while `init` loads the file for the vendor's version, `202504.cil`, which the build assembles from `compat/202504/202504.cil` files (found by the first validation of build 5: `sepolicy.mapping` FAIL, the vendor policy's 35 references to the two app domains bound to nothing). It holds the three entries stock A17's 202504 mappings have for these domains, including the A17-only `moto_app_202504` → `moto_camera_app` (vendor rules for Motorola apps apply to the A17 camera). **Changed** `vendor_qtelephony.te`: `hal_client_domain()` for the ATFWD and IMS-VT HALs (as stock A17), which on Android 17 adds `memfd_file` rules; the two HAL attributes are declared in `sepolicy/public`. Both found by comparing the effective permissions with stock A17 (`sepolicy_diff.py`): after them, what stock allows the two domains on labels that exist here and this image does not is down to the two service lookups known from A16 (`recovery_service`, `vr_manager_service`) | diff of `vendor_sepolicy.cil` A16/A17, A17 IMS manifest, A17 `system_ext_seapp_contexts`; `system/sepolicy/compat/Android.bp` (`system_ext_202504.cil`); stock A17 system_ext and product mapping files; stock A17 `system_ext_sepolicy.cil` A16/A17 diff |
| Privileged-permission allowlists | IMS and camera: unchanged (stock A17 grants exactly the A16 lists; every privileged permission the A17 apps request is covered). New: `microg/privapp-permissions-vantage-microg.xml` | `permissions.json` A16/A17; requested permissions against LineageOS 24.0 protection levels |
| Telephony overlays | unchanged (`config_ims_mmtel_package`, IWLAN packages, eUICC values): the A17 stock overlays hold the same values | `dump_overlays.py` on A17 (155 overlays, 3,586 values) |
| Framework overlay review (new) | Of the 403 values stock A17's `/product` and `/system_ext` overlays set on the framework, most are Google/Motorola app wiring, optional cutout emulations, fonts and navigation modes. The stock **`/vendor`** overlays, which the phone keeps under any system image, already hold brightness curves, Night Light, refresh rates, colour modes and rounded corners. What only `/product` holds and describes hardware went into the new **`overlays/VantageDeviceOverlay`** with stock's values: punch-hole cutout and status-bar height, under-display fingerprint position, ambient display, proximity suspend during calls, the two display/suspend decoupling flags, mobile MTU and per-technology TCP buffers (13 values; 2 more stock values do not exist in LineageOS's framework and were left out). Not carried over: Motorola/Google package names, Motorola-private keys (`zz_moto_*`), double-tap-to-wake (needs Motorola's touch service), doze timing tuning. **Corrected after the first boot (r2):** the review covered only overlays of the framework and missed two screen values. Stock's `/product` overrides the `/vendor` corner radius (24dp) with `rounded_corner_radius` 100px (now in `VantageDeviceOverlay`), and stock's SystemUI overlay sets `rounded_corner_content_padding` 30px (new `overlays/VantageSystemUIOverlay`). Without it the status bar clock sat almost in the left rounded corner (owner's screenshot): AOSP's padding is 0 and only the right side keeps the privacy-dot padding | `reports/overlay-review.txt`; every key checked against LineageOS 24.0 `core/res/res/values` and SystemUI `res/values` |
| Refresh rate setting (new, r2, owner's request) | Stock's own selector (`com.motorola.coresettingsext`, Auto/60/120/144 Hz) is a Motorola app, not ported. LineageOS has "Maximum refresh rate" and "Minimum refresh rate" lists in Settings > Display, hidden by default; `overlays/VantageSettingsOverlay` shows them. They list the display's modes, on this panel 165/120/90/60/30/24 Hz (A16 captures). The 165 Hz mode has no seamless switch to the others, and Android 17 keeps the display in the default mode's group (120 Hz), so 165 Hz takes Maximum = 165 and Minimum = 165 (the maximum setting outranks the minimum one). Defaults unchanged: peak 120 Hz from the stock `/vendor` overlay | Lineage `packages/apps/Settings` (`PeakRefreshRateListPreferenceController`, `MinRefreshRatePreferenceController`, `lineage_config.xml`); `services/core/.../display/mode` (`VoteSummary.selectBaseMode`, `Vote` priorities) |
| UI smoothness (new, r3, owner's request) | Measured on r2 (hardware-tested, `reports/ui-smoothness-r2.md`): the GPU works (SurfaceFlinger GLES and HWUI Vulkan on the Adreno 829), but quick settings and the app drawer had about 40 % janky frames, 60 fps instead of 120: with blur, every layer is GPU-composited and SurfaceFlinger takes about 10.5 ms per frame while the CPU stays at 556 MHz; with window blurs off, 1-2 %. Stock avoids this with Qualcomm's own SurfaceFlinger (`libdolphin.so`), `QPerformance`/`UxPerformance` and a perf HAL that can announce itself. r3, in `properties.mk` (product, read after the vendor): `debug.sf.use_phase_offsets_as_durations=1`, so AOSP's SurfaceFlinger uses the vendor's own `debug.sf.*.duration` values (10.5 ms for itself instead of 7.3 ms at 120 Hz; about one frame more latency), and `debug.sf.enable_adpf_cpu_hint=true` (SurfaceFlinger's ADPF hint session; the vendor's power HAL supports sessions and may set scheduling of surfaceflinger). `sepolicy`: stock's `vendor_wlc_public_prop` with its 202504 mapping and the `vendor.mpctl.init.complete` line, whose absence made the perf HAL's write fail at every boot. Not ported: Qualcomm's SurfaceFlinger extensions and boost jars (stock binaries in the framework) | trace and `dumpsys` on r2; LineageOS `frameworks/native` (`SurfaceFlingerDefaultFactory.cpp`, `VsyncConfiguration.cpp` `validateSysprops`, `FlagManager.cpp`, `PowerAdvisor.cpp`); stock A17 `system_ext_property_contexts`, mapping `202504.cil`, `vendor_sepolicy.cil` (`hal_power_default` → `surfaceflinger_202504` setsched), vendor `task_profiles.json` (`NoResetUclampGrp`); new checks `built.sf_timing`, `sepolicy.mapping:vendor_wlc_public_prop` |
| Charging limit (new, r4, owner's request) | Stock's battery protection: Motorola's framework (`BatteryService$MotoAdaptiveCharging` in stock `services.jar`) reads `charging_upper_limit`/`charging_lower_limit` from Motorola's battery-configuration provider and calls the stock vendor HAL `motorola.hardware.health.IMotoHealth/default` (AIDL V3) `setChgLimits(lower, upper)`; the vendor service writes `/sys/module/qpnp_adaptive_charge/parameters/{lower,upper}_limit` (charging stops at upper, resumes at lower; upper 1..100, lower below it, negative upper = off; both read `-1` on r3). LineageOS has the setting already (Settings > Battery > Charging control, modes Auto/Custom/Limit, limit slider 70-100 %, default 80 %, recharge margin 10), but it needs the `vendor.lineage.health` HAL, which the stock vendor lacks, so the page was hidden. New **`patches/lineage-sdk`**: `ChargingControlController` falls back to `MotoChargingControl`, an `IChargingControl` adapter offering LIMIT mode over IMotoHealth (transaction codes and argument order from stock's generated proxy); 100 % = off. Runs in system_server, which the stock vendor policy already makes a client of that HAL (`hal_mothealth_client` = system_app, system_server), so no SELinux or VINTF change. Found while reading the controller: with a LIMIT-only HAL, LineageOS also hands the Auto and Custom schedule modes to its Limit provider, whose time-based callback was not implemented (the base class throws, in system_server, once such a schedule is active while charging; Auto is the default mode). The same patch implements it: hold at 80 % in the scheduled window, lift the limit early enough to reach 100 % at the target time | stock `services.jar` (dexdump), vendor `motorola.hardware.health-service` (strings, disassembly of the range check), `motorola.hardware.health.aidl-V3-ndk.so` symbols, stock `vendor_sepolicy.cil`; LineageOS `lineage-sdk` health code and `vendor.lineage.health` V2; new checks `patch.image:lineage-sdk`, policy queries system_server -> `hal_mothealth_aidl_service` find, `hal_mothealth_default` call |
| Carrier configuration (313390) | values unchanged. It was transcribed from stock's `dumpsys carrier_config`, whose values come from Google's carrier settings, not from the firmware. One key renamed: Qualcomm's `allow_video_call_in_low_battery` is `allow_video_call_in_low_battery_bool` in the A17 `ims-ext-common.jar` (and in AOSP); the value (true) is also the default. New check: video calling must stay off (`carrier.video_calling_off`) | FIRMWARE_A17.md section 3 item 2; `carrier.config_keys` (dex strings of the image's framework and stock IMS library) |
| APN database | the A17 `/product/etc/apns-conf.xml` (changed content), installed instead of LineageOS's generated list, which for Optimum 313390 lacks the stock initial-attach and tethering APNs. Needs the new `patches/vendor/apn` (switch `lineage_apn.use_device_apns`) | in `proprietary-files.txt`; BUILDING.md section 9 |

## The Android 16 fixes, one by one

| A16 fix | Decision | Reason (static) |
|---|---|---|
| `init/init.vantage.media.rc` (camcorder profile file) | **keep** | LineageOS 24.0 `frameworks/av` `MediaProfiles.cpp` still reads `ro.media.xml_variant.profiles`; the A17 vendor still publishes only `ro.media.xml_variant.codecs` (`init.qti.media.rc`, `init.qcom.rc`) and ships `media_profiles_canoe_sku{1,2,3}.xml` |
| `ro.vendor.qti.va_aosp.support=1` readable only by the camera HAL | **keep** | A17 `libqti_vndfwk_detect_vendor.so` still reads it; the A17 vendor policy keeps the same domains; `validate-image.sh` re-runs the allow/deny queries on the combined policy |
| `VantageRilReady` (ATEL "telephony ready" OEM hook) | **keep** | A17 RIL property database: `persist.vendor.radio.poweron_opt` default 1 (upgrade scripts 0010-0012); `vendor.qti.hardware.radio.qcrilhook` `IQtiOemHook/oemhook0,1` unchanged. The stock sender is still `com.qti.phone`, not ported |
| Audio vendor-extension loader (`audio/vendorext`) | **keep** | A17 `libaudiohalvendorextn.so` still exports `registerInterface`; stock still sets `ro.audio.ihaladaptervendorextension_enabled=true`; the audio HAL is still AIDL `audio.core` V3. Symbol linkage re-checked on the image |
| QcRilAm patch (`patches/packages/apps/QcRilAm`) | **keep, and QcRilAm is now added by us** | TrebleDroid is not in the tree; the bridge is pulled by the local manifest at the A16 commit `dc599b67`, so the patch applies unchanged. The A17 vendor serves the same `vendor.qti.hardware.radio.am` `IQcRilAudio/slot1,2`; stock A17 dropped its own client (`QtiTelephonyService`) |
| `patches/system/core` (`ro.carrier` from `androidboot.carrier`) | **keep** | LineageOS 24.0 `init/property_service.cpp` has no such entry; the patch applies (offset -10 lines); the A17 vendor ships `ro.carrier=unknown` and reads `ro.carrier` in four init scripts, `xtra-daemon` and five libraries; stock A17 `init` exports it |
| (new) `patches/vendor/apn` | **added** | lets the product ship the stock APN database instead of LineageOS's (see the APN row above); not security-related |
| `patches/frameworks/native` (screenshot LUT descriptor) | **drop** | upstream: LineageOS 24.0 `ScreenCaptureOutput.cpp` already passes `aidlLuts.pfd.release()` |
| `VantageImsNetwork` (IMS network request) | **keep** | A17 `CneApp` is still a non-privileged `/vendor` app signed with Motorola's key, so it still cannot hold the restricted request under another platform key |
| `VantageFrameworkOverlay` (WebView provider list) | **drop** | it undid TrebleDroid's list, which starts with Google WebView: AOSP 16/17 takes the first "available by default" entry as the only default (A16 first boot: no WebView). LineageOS's own overlay (`vendor/lineage/overlay/common`, `config_webview_packages.xml`) also lists Google WebView (four channels) before `com.android.webview`, but LineageOS's `SystemImpl.getWebViewPackages()` drops providers that are not installed (`isProviderAvailable`) before the default is chosen, so the default here is `com.android.webview`. (Corrected after the first validation, which modelled AOSP and failed; step 3 had wrongly read only the framework's base list.) `check_image_composition.py` now detects the filter in the image's `services.jar` |
| TrebleDroid's run-time properties | **not needed** | none of them is set by stock; without them the phone behaves as stock does (FIRMWARE_A17.md section 4) |

## New for Android 17 / LineageOS

| Item | What |
|---|---|
| `seapp_contexts` line for `com.qti.phone` | see above |
| Video calling | not offered: the A17 IMS app's video back end is the system_ext daemon `imsvtdaemon`, not ported (binary, AIDL library, own SELinux domain); voice calls do not reach that code. `validate-telephony.py` fails the build's validation if video calling gets enabled for the carrier |
| microG | `vendor/motorola/vantage/microg` (README there): official release APKs, LineageOS's built-in spoofing (compiled into `userdebug`/`eng` builds), derived allowlist, `validate-microg.py` |
| `ro.debuggable=0` | LineageOS sets `PRODUCT_NOT_DEBUGGABLE_IN_USERDEBUG` for `userdebug` builds: unlike the A16 image there is no `adb root` (static: `/system/build.prop`). If `adb` does not see the guest, USB debugging has to be turned on in Developer options (not established statically whether it starts on). Kept as LineageOS ships it; `PRODUCT_NOT_DEBUGGABLE_IN_USERDEBUG := false` in `lineage_vantage.mk` would restore A16's behaviour (owner's decision, security-relevant). microG is unaffected (see its README) |
| SELinux mapping for a 202504 vendor | `sepolicy/private/compat/202504/202504.cil`, see the first table |
| `preflight.py` | the policy compile now includes `plat_sepolicy_genfs_<vendor genfs version>.cil`, as Android 17 `init` does (`init/selinux.cpp`: missing file with version >= 202504 is fatal) |
| Product | `device/motorola/vantage/lineage_vantage.mk` inherits `lineage_gsi_arm64`; release config `cp2a`; sets `BUILDING_LINEAGE_GSI` (BUILDING.md section 9) |
| Stock files vs LineageOS's open-source Qualcomm modules | LineageOS builds `ims-ext-common`, `qti-telephony-utils` and `libaudiohalvendorextn` from source. The stock A17 binaries replace them (`prefer: true` prebuilts); the two permission files come from LineageOS's modules because they are byte-identical to stock (checked by SHA-256 at generation). So the image carries exactly the pinned stock files, as on A16 |
